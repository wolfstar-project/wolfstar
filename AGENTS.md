# AGENTS.md - wolfstar Bot

## Project Overview

Discord bot built on **Sapphire Framework** (discord.js). TypeScript, PostgreSQL (Prisma ORM).

## Conventions

- **Language:** TypeScript (strict mode, `@sapphire/ts-config`)
- **Module system:** ESM (`"type": "module"`)
- **Path aliases:** `#lib/*`, `#common`, `#types`, `#utils/*` (→ `src/lib/utilities`), `#root/*` — one map in `projects/bot/scripts/aliases.ts`, shared by `stars.config.ts` and `projects/bot/vitest.config.ts` (same layout as [staryl](https://github.com/wolfstar-project/staryl))
- **Naming:** camelCase for files/variables, PascalCase for classes
- **Build tool:** tsdown
- **Formatter/Linter:** oxlint + oxfmt, prettier
- **Test runner:** vitest (globals enabled, setup in `tests/setup.ts`)
- **Package manager:** pnpm (workspace)
- **CI:** `.github/workflows/continuous-integration.yml` has one job per check, as wolfstar.rocks does: lint (root install only), typecheck, unit tests (JUnit and coverage to Codecov), knip, i18n (the locale tests and the generated types of the i18n keys and of the command options) and build. The jobs that read the bot run `stars prepare` first, and the ones that import `wolfstar-database` build it. `pnpm typecheck` has no known errors: `scripts/` has its own `tsconfig.json` for the Node types
- **Unused code:** `pnpm knip` (`knip.config.ts`) fails on unused files, unused or unlisted dependencies and unresolved imports, and runs in CI. The unused exports are only warnings: the exports of `src/lib` are auto-imported, which knip cannot see. The pieces are entry files; a new directory of pieces must be added to the `entry` of the bot, and the barrels of `src/lib` are ignored
- **Auto imports:** the Stars CLI auto-imports every exported value of `src/lib/**` and of the framework (`.stars/imports.d.ts`). Import a class or enum that is only used as a type in its own `import type` statement (an inline `type X` in a mixed import is declared twice), and export a generic class apart from its declaration (`class X<K, V> {}` then `export { X }`): the scanner reads `, V` as a second export
- **TypeScript config:** `stars prepare` (and `stars build`, `stars dev`) writes `projects/bot/.stars/tsconfig.app.json`, `tsconfig.node.json` and `imports.d.ts`, which are not tracked. `projects/bot/tsconfig.json` only references the two, and `src/tsconfig.json` and `tests/tsconfig.json` extend `tsconfig.app.json`. The CLI no longer writes a `.stars/tsconfig.json`: do not extend it. Anything that reads the config before a build (knip in CI) needs `stars prepare` first
- **Command options:** `stars codegen` writes `projects/bot/src/@types/commands.d.ts` (`codegen.commands` in `stars.config.ts`, do not edit it): the options of every registered command, keyed by its path (`'slowmode'`, `'whois channel'`). It reads the built bot, so run `stars build` first after changing a builder. While `stars dev` runs, `stars codegen` fails with `LOCAL_COMMANDS_UNAVAILABLE`: it writes `i18next.d.ts` first, the watcher rebuilds and `dist/main.mjs` is gone when the commands are read. Run it again with a copy of the config whose `codegen` is `{ i18n: false, commands: true }` (`--config`), or stop the watcher. The CI job `i18n` runs `stars codegen --check` as a whole: it builds the bot and starts it with throw-away values (`NODE_ENV=test`, `DISCORD_TOKEN`, `DISCORD_PUBLIC_KEY` and `REDIS_PASSWORD` of 40 characters or more, since Varlock refuses a short secret) next to a Redis service container, which is all the bot needs to reach `client.load()`. Type the options of `chatInputRun` with `Command.OptionsOf<'path'>` (the `Command` of `@wolfstar/http-framework` and the one of `@wolfstar/plugin-subcommands-advanced` both have it). Do not write an interface for the options by hand
- **Framework version:** `@wolfstar/http-framework` `^6.5.1` (the `/module` of `@wolfstar/shared-http-pieces` asks for 6.5 and `@wolfstar/kit` 0.3). The prerelease it was pinned to before (and the override of `pnpm-workspace.yaml` that gave it to the plugins) is gone: 6.3.2 shipped the fix of `handleError` (stars-components#321). `patches/` holds what `pnpm-workspace.yaml` patches on install (`patchedDependencies`)
- **Command registration:** the bot writes its commands to Discord when it starts (`commands: { register: 'on-start', when }` of the client, in `createClient()`): once the HTTP server listens, the registry compares the loaded commands with the deployed ones and creates or updates only what differs, and a failure is only logged. `when` keeps it to one process, since the framework takes no lock: the gateway (a worker never listens) and, with the sharder, the shard `0`. A command the bot no longer defines stays deployed (`removeUnknown` is off): remove it with `stars commands clean`. `stars codegen` and `stars commands` set `STARS_COMMANDS_DUMP=1`, which skips it. The order of the options is compared too, so `plugin-subcommands-advanced` (2.2.1 and later) adds the subcommands in the order of their names instead of the order the pieces load, which changed at every start; a description must not hold the variation selector of an emoji (`U+FE0F`), which Discord drops (`tests/locales/commands.test.ts`)
- **Shared utilities:** `projects/shared` (`wolfstar-shared`) holds the code that does not need the bot: no `container`, framework, plugin nor i18n. The units of time (`seconds`, `Time`), the comparators, iterators and parsers that were in `src/lib/common`, and from `src/lib/utilities` the timers, the permission bits, the reading of a submitted modal (`getModalValue`), the time zones, the zalgo check, `escapeMarkdown`, the word expressions (`RegexCreator`) and the links (`TLDs`, `urlRegex`, `PhishingHostnames`). Import it from `wolfstar-shared`; `stars.config.ts` lists it in `imports.presets` too, so its exports are auto-imported as they were from `src/lib`. The bot reads it built, as it does `wolfstar-database`: build it (`pnpm --filter wolfstar-shared build`) before `stars prepare`, which reads its types for the auto-imports, and the CI jobs and the Dockerfiles do. The tests read its sources (an alias of `vitest.config.ts`), and its own are in `projects/shared/tests`. It has no `const enum`: the bot reads its enums from the built declarations, where `verbatimModuleSyntax` cannot inline one. What reads `container`, the gateway or the translations stays in the bot
- **Sentry:** `@wolfstar/shared-http-pieces` is in `modules` of `stars.config.ts` (its `/module`, which installs the shared commands, listeners and locales: there is no `/register` import in `lib/setup/all.ts`), and its `initializeSentry` sets Sentry up once (`initializeApp()` in `lib/setup/all.ts`), when `SENTRY_DSN` is set. The bot has no `@sentry/node` of its own: a second copy of the SDK would not report to the client that one set up. Take the SDK as `Sentry` from `@wolfstar/shared-http-pieces` (`Sentry.captureException`), check `isSentryInitialized()` before reporting, and give another integration or option to `initializeSentry` rather than calling `Sentry.init` (the integrations of `initializeApp` are `getSentryIntegrations`, see **Tracing**)
- **MCP servers:** `.mcp.json` has the ones the agents use: the documentation of Varlock (`varlock-docs-mcp`), of the framework and the Stars CLI (`stars-docs`), of the Discord API (`discord-docs`) and of every other library (`context7`), plus `sentry`, `prisma` and `railway`, which ask to sign in. None holds a secret; do not add one that needs a key in the file

## Plugins

`@wolfstar/plugin-api`, `plugin-i18next`, `plugin-subcommands-advanced`, `plugin-gateway`, `plugin-cache`, `plugin-broker` and `plugin-sharder` are registered automatically: the Stars CLI injects `import '@wolfstar/plugin-*/register'` into `src/main.ts` for every `@wolfstar/plugin-*` package in `dependencies`. Do not add manual `/register` imports; add or remove the dependency instead.

- **Logger:** `@wolfstar/plugin-logger` is the one plugin not registered that way: `stars.config.ts` lists its `./module` in `modules` (the CLI skips the injected `/register` for a package listed there, and the two together would install the hooks twice) with the `evlog` option, so `container.logger` writes through evlog. The level is `LOG_LEVEL` (`trace` to `fatal`, or `none`; `info` by default), which `getLoggerOptions()` (`lib/utilities/logger.ts`) gives the logger as the `logger.level` client option, of the client of the shard manager too: the module's options are written into the build, so the level stays out of them and can change without building again. evlog prints the logs itself, one JSON line each in production, and hands them to the drain of `src/evlog-drain.ts` (`defineEvlogDrain` of `@wolfstar/plugin-logger/evlog/plugin`, named by its path in the config because the options of a module cannot hold a function), which sends them to Sentry as structured logs (`createSentryDrain` of `evlog/sentry`, in batches with retries, `pipeline: true`) and does nothing when `SENTRY_DSN` is not set. The DSN is a secret and the options of a module are written into the build, so the drain reads it from the environment when it sends and it is never in the config. The plugin also drains one wide event for each interaction (command, component, modal; not autocomplete), with its outcome, duration, guild, channel and user; `useInteractionLogger()` of `@wolfstar/plugin-logger/evlog/plugin` adds fields to the one being handled. evlog batches its events, so the process flushes the logger when it stops (`closeTelemetry`, which closes the logger with `closeLogger` and exports the last spans with `flushTraces`, and `closeLoggerOnShutdown` in `lib/utilities/shutdown.ts`: on `SIGTERM` and `SIGINT` of the gateway process, after the shard manager destroys its shards, and when the manager closes a shard); a worker stops through the signals of its broker consumer and does not flush. The drain sends logs only: errors still reach Sentry as issues through `initializeSentry` (the drain's `issues` option is off, or each would open two), see **Sentry** above.

- **Gateway:** the bot runs the Discord gateway in-process with `@wolfstar/plugin-gateway`. `createClient()` in `src/lib/Client.ts` builds a `GatewayClient` (intents, shards) backed by a `@wolfstar/plugin-cache` Redis cache (`container.redis`, prefix `wolfstar:cache`) and a Redis session store (prefix `wolfstar:sessions`, so a restart resumes the shards instead of identifying again), and `loadAll()` calls `container.gatewayClient.start()`, which loads the pieces, serves HTTP interactions and connects the shards. Gateway events reach regular listener pieces (`EventGatewayListener`). There is no separate gateway process. `@wolfstar/plugin-broker` can publish every dispatch onto a Redis stream for workers to replay: `createClient()` forwards them with `forwardGatewayDispatches` when `BROKER_ENABLED=true` (stream `BROKER_STREAM`, trimmed to `BROKER_MAX_LENGTH`); it is off by default. A second process started with `BOT_MODE=worker` never connects to Discord: it reads the stream as a member of the `BROKER_GROUP` consumer group (named `BROKER_CONSUMER`, unique per replica) and replays the dispatches on a `GatewayClient` sharing the same Redis cache (`replayGatewayDispatches`), with no HTTP server and no API. Run exactly one gateway process. A dispatch is handled by one process only: the listeners of the events of Discord are registered with `RegisterAsDispatchListener` of `@wolfstar/plugin-gateway`, which does nothing on a client that forwards its dispatches (`forwardGatewayDispatches` marks it, the client is asked on every event), so with the broker on the workers run them and without it the gateway does; the events of the gateway itself (`clientReady`, the ones of the shards) are not replayed and keep `RegisterAsGatewayListener`, and the decorator refuses them. A new listener of an event of Discord uses `RegisterAsDispatchListener`. The `guildDelete` the gateway emits for the guilds a `READY` no longer lists is forwarded too, so the workers handle it
- **Sharding:** `@wolfstar/plugin-sharder` (`src/lib/sharder/`), off by default. With `SHARDER_ENABLED=true` the started process is the shard manager (`isShardManager()` in `main.ts`): it never connects to Discord, it spawns `SHARDER_CLUSTERS` shards (one per CPU core by default) as `node:cluster` workers running the same script, splits Discord's recommended gateway shards between them and paces their identifies. The shards share the ports of the interactions endpoint and of the API. In a shard, `createClient()` sets `container.shard` (`ShardClient`, `null` in a single process) and gives its gateway shards to the `GatewayClient`. State kept in memory is per shard: a settings write is broadcast (`broadcastShardMessage({ type: 'settingsUpdate' })`) so the other shards drop their cached copy; add a message to `ShardMessages` and listen with `onShardMessage` for anything else that must cross processes. The manager process also creates a plain `Client` that never listens, for `container.logger` and for the listeners of its own events: the `SharderListener` pieces of `src/listeners/sharder/`, the only ones it loads; they are disabled in every other process. The moderation locks and the analytics message counter are not shared.
- **Scheduled tasks:** `@wolfstar/plugin-scheduled-tasks` (BullMQ on a second Redis connection, `container.redisTasks`, queue `tasks`, prefix `wolfstar:bull`) runs the `ScheduledTask` pieces in `src/scheduled-tasks/`. It is given to the client in `createClient()` (`plugins: [scheduledTasks()]`) and not through `modules` in `stars.config.ts`, because the options of a module are written into the build and the connection holds the Redis password. Schedule with `container.tasks.create({ name, payload }, delay)`; type the payload by augmenting `ScheduledTasks`. The tasks run on the gateway process, the one that calls `listen()`. A task that needs the gateway sets `waitForReady: true` in its options: its job waits for the `ready` option of `tasks` (`gatewayClient.isClientReady()`), and is pushed back when the shards are still not connected after 30 seconds (`poststats`).
- **Shared locks:** the queues of a process (`AsyncQueue`) do not keep another shard, a worker or the API from writing at the same time. What reads rows and writes them back takes a lock in Redis as well (`withSharedLock` and `acquireSharedLock` in `lib/utilities/locks.ts`, key `wolfstar:locks:<key>`, held 15 seconds at most): the settings transaction (`settings:<guildId>`, which reads the settings again from the database under it), the writes of the auto-moderation rules (`automod:<guildId>`), the limits of the automatic purges and deletions (`cleanup:<guildId>`), the number of a new moderation case (`moderation-cases:<guildId>`, read again from the database under it) and the toggle of a user preference. Without a ready connection (the tests) nothing is locked
- **Permission levels:** the `moderator` and `administrator` preconditions (`src/preconditions/`, on the `PermissionLevelPrecondition` base of `lib/structures/commands/`) apply the levels of `hasCommandPermissionLevel`. Name them in the `preconditions` option of a command or of an interaction handler (`@ApplyOptions<Subcommand.Options>({ preconditions: ['administrator'] })`). A subcommand is run through its parent, so the option goes on the parent and covers all its subcommands, and its autocomplete; a parent whose subcommands have different levels (`/settings`, `/mute`) uses `RequiresCommandPermissionLevel` on the subcommands instead. The denials reach `chatInputCommandDenied`, `contextMenuCommandDenied` and `interactionHandlerDenied` (`src/listeners/commands/`), which reply to the user; a handler whose clicks are not all of one level (`conf`, `report`, `commands`) checks with `hasCommandPermissionLevel` itself. The `commandsEnabled` precondition is global.
- **Emojis:** the emojis of the bot are the **application emojis** of Discord, and staging, beta and production are three applications, each with its own IDs for the same names. `src/lib/utilities/emojis.ts` has the names (`EmojiDefinitions`, the source of truth: add an emoji there and upload it with that name to every application), `loadApplicationEmojis()` reads the ones of the application the bot runs as (`CLIENT_ID`, at the start of `loadAll()`, `GET /applications/{id}/emojis`) and `Emojis.<Name>` writes `<:name:id>` when it is used. An application that lacks an emoji gets the one the bot used before, or the Unicode emoji of its definition for the ones it never had (the `checked`/`unchecked` checkbox the menus show a setting that is on or off with (on a button it stands alone, with no label), the `warning` triangle of what the user is warned about, the `ArrowL`, `ArrowR`, `ArrowFastL` and `ArrowFastR` arrows the menus go from a page to another, to a group and back with, the `back` return arrow of the buttons that go back (drawn, not from the Figma file: it has none, only chevrons), the `hourglass` clock of what expires, the `refresh` arrows of a button that shows a menu again and the `add` plus of one that adds an entry (the `reload` and `add` icons of the Discord assets, `Refresh` and `Add` in the sheet), the `module_appeals` scales (drawn, `Appeals` in the sheet, `module_appeals` being one of the `module_*` ones), the `package` box of the export and import of the settings and the `export` and `import` cloud arrows of their buttons (`upload-to-cloud` and `download-from-cloud` of the Discord assets, `Export` and `Import` in the sheet; the box is drawn, `Package`), the `experimental` test tube of what is experimental (drawn after the Unicode one, in the grey of the others, in `Icons (Brand WolfStar)`, page `Emoji`, at the end of the `Normal` grid, with the coloured one as `Experimental (color)`; the other emojis that were drawn and not cut from the Discord assets are there too: `Back`, `Reports`, `Honeypot`, `Checked` and `Unchecked`), the animated `loading` spinner (a GIF, drawn, the one `{{LOADING}}` writes), the `module_*` ones of the select menu of `/settings server`, the `category_*` ones of the categories of `/commands`, the `badge_*` ones `/whois user` lists from the public flags of a user, `getUserBadges`), and the missing names are logged once at the start. A component takes an emoji as an object, not as text: `getEmojiComponent('Checked')`. The `{{GREENTICK}}`, `{{REDCROSS}}` and `{{LOADING}}` variables of the texts are getters for the same reason
- **Moderation tasks:** a case with a duration gets a `moderationEnd*` job (`src/scheduled-tasks/moderation/`, on the `ModerationTask` base) that undoes it when it expires. The `moderationEntryAdd` listener creates it with the ID `moderation-<guildId>-<caseId>` (`getUndoTaskId`), and `moderationEntryEdit` reschedules it when the duration changes or removes it when the case is completed or archived; `ModerationManagerEntry#fetchTask()` finds it. A task that throws is tried again 20 seconds later, for two hours (`UndoTaskJobOptions`), and a job that ran out of attempts stays in the queue as failed. `ModerationTask` completes the case when the undo worked or Discord refused it for good (a client error), and fails the job for anything else, a missing permission of the bot included (`requirePermissions`). `poststats`, `syncResourceAnalytics`, `autoPurge` and `honeypotUpkeep` are the repeated tasks (cron patterns).
- **Role of a moderation action:** the `mute` and `restrict` commands (`SetUpModerationCommand`) need a role. When it is not set up, who is not an administrator is told to ask one, and an administrator gets a prompt (`lib/moderation/structures/RoleSetupPrompt.ts`, thrown from `inhibit` as a `ModerationCommandPrompt`, which `ModerationCommand#chatInputRun` answers with): a select menu of the roles to use one the server has, a button to create a new one that is configured in every channel (`RoleModerationAction#setup`), and one to cancel. The `roleSetup` interaction handler does what is picked (`roleSetup.<ownerId>.<verb>:<type>`, administrator level). A click does not carry the options of the command, so the command and its options wait in Redis meanwhile (`wolfstar:moderation:role-setup:<guildId>:<ownerId>:<type>`, 15 minutes), and the handler runs the command again with them once the role is set up (`ModerationCommand#execute`, the part of `chatInputRun` that does not answer the interaction); when it is not there anymore, the administrator is told to run it again. `/mute create` sets the role up without the prompt
- **Role of an action taken by hand:** a mute takes the roles of the member and keeps them in its case, so a moderator who takes the muted role away in Discord used to leave the member with no role and the case in course. The `guildMemberUpdateActionRoleRemoved` listener (`src/listeners/guilds/members/`) takes the role that goes (the muted one, or the one of a restriction) for the undo of the case that is in course: `action.undo` gives the roles back, completes the case and drops its task, in the name of who took the role when the bot can read the audit log. A role the bot takes itself is marked in Redis first (`markOwnRoleChange` in `lib/moderation/common/roleChanges.ts`, `wolfstar:moderation:role-change:<guildId>:<userId>:<roleId>`, 30 seconds, with `:add` at the end for a role the bot gives), since the undo may run on another process than the one the gateway tells. The other direction is opt-in with `moderation.track-roles` (`GuildModeration.trackRoles`, off by default, the column added by hand as the one of the time zone): the `guildMemberUpdateActionRoleAdded` listener takes the muted role, or a restriction role, a moderator gives by hand for the action: `action.apply` makes the case (a mute takes the other roles and keeps them), in the name of who gave the role when the audit log says so (`fetchRoleChangeExecutor` in `lib/moderation/common/manualRoles.ts`, which looks twice, a moment apart, since Discord may tell the bot before it writes the entry). A member the action is already in course for is left alone (the sticky role that is given back when they join again), and so is a role the bot gave itself (`RoleModerationAction#handleApplyPre` marks it). No direct message is sent. Taking the role away is always handled, since a case in course with no role is a state that is wrong whatever the server wants. It needs the member to be cached, which is how the roles it had are known. When the role itself is deleted while the action is in course for somebody (`getUsersInCourse`), the `roleDelete` listener makes it again (`RoleModerationAction#restore`): a new role, saved as the one of the action, configured in every channel and given to the members whose case is in course. It is tried three times, 5 and 30 seconds apart (`retryWithDelays`), and an attempt uses the role an earlier one made; after that it is logged. The settings forget the deleted role before any of this, so an action that is in course for nobody, or whose role could not be made, is left with no role and never shows one that is not there
- **Who did it, from the audit log:** `rawGuildAuditLogEntryCreateLoggerTrack` gives every audit log entry it knows to the `LoggerTypeManager` of its kind in `LoggerManager` (`ban`, `unban`, `kick`, `nickname`, `roleUpdate`, `timeout`, `prune`: `lib/moderation/managers/loggers/`), and a listener that needs to know who did something `wait`s on it with the ID of the target: the entry the gateway gives resolves it, and when none comes in 3 seconds the audit log is read once (nothing without `View Audit Log`). A ban or an unban tracked with `moderation.track-bans` has the moderator and the reason of the entry (`guildBanAdd`, `guildBanRemove`), and an entry of the bot itself is left to the action that made the case. A kick made in Discord is a case with `moderation.track-kicks` (`rawMemberRemoveKickTrack`, off by default since every member that leaves costs a request to the audit log: Discord only says a member was kicked there); a timeout already was one with `moderation.track-timeouts`. The logs of a nickname change and of an edited role add a `Changed by` line (`events/guilds-logs:changedBy`) when the entry is known, which delays them until it is, 3 seconds at most. The logs of deleted messages do not: the entry arrives after the message was deleted, a log that is sent cannot be edited (it may be the message of a webhook) and reading the audit log for every deleted message is too many requests
- **Voice mute of a member who comes back:** Discord forgets the server mute of a member who leaves the server, so who was voice muted joined again and could talk with the case still in course. The `voiceStateUpdateVoiceMuteRestore` listener (`src/listeners/guilds/members/`, the `GuildVoiceStates` intent the client already asks for) mutes them again when they connect to a voice channel, since Discord only mutes a member who is connected: `shouldRestoreVoiceMute` (`lib/moderation/common/voiceMutes.ts`, a pure function) only lets through the update of a member who came into a channel, from none or from another one, and is not server muted, so the other updates of a voice channel (a self mute, a stream) cost nothing. The mute is given back with the API, with no case and no direct message: it is the same voice mute, and it stops with it, since what is asked is whether the latest `VoiceMute` case of the member is in course (`getUsersInCourse`), which `/vmute remove` and the end of a temporary one both end with an undo. A member who has none is remembered in Redis (`wolfstar:moderation:not-voice-muted:<guildId>:<userId>`, 10 minutes, `markNotVoiceMuted`), so the cases are not read every time somebody connects, and `ModerationActionVoiceMute#apply` forgets it once the case is written. Without `MuteMembers` nothing is done nor remembered. A mute a moderator takes by hand while the case is in course is left alone until the member connects again; no listener takes a server mute for a manual action (the one of the timeouts only reads `communication_disabled_until`)
- **Answer of a moderation command:** a command that made a case (`warn add`, `mute add`, `mute remove`, `ban`…) answers with a small embed (`renderModerationOutput` in `ModerationCommand.ts`) with the case, the user and, when the server wants it shown, the reason. It is green; yellow when the case was made but the user could not be sent the direct message (the action sets `directMessageUndelivered` on its `Data`, and says so in a line of the embed); and a failure is a small red embed (`renderModerationFailure`). The colors are the status ones, not the ones of the type of case, which the embed of the case keeps
- **Predefined reasons:** a guild defines up to 25 reasons (`MaximumModerationReasons`), each with a short alias, as rows of `GuildModerationReason` (`projects/database/src/settings/reasons/`, which the contract controls). `/reasons add|remove|list` (`src/commands/Management/reasons*`, administrator level) manages them, and the `reason` option of every moderation command autocompletes them and takes an alias for its reason (`resolveModerationReason` in `lib/moderation/reasons.ts`, in `ModerationCommand#execute`; an alias is matched whatever its case, any other text is written as it is). The autocomplete of a subcommand reaches its parent, so the parents of the moderation subcommands (`warn`, `mute`, `ban`, `timeout`, `vmute`, `role`, `restrict`, `unrestrict`) answer it with `replyModerationReasonAutocomplete`. They are cached per guild and broadcast as `moderationReasonsUpdate`
- **Confirmation after a recent case:** with `moderation.confirm-recent` (`GuildModeration.confirmRecentMinutes`, minutes, 0 by default: never), a moderation command whose target has a case made within those minutes (`findRecentCase` in `lib/moderation/structures/RecentCasePrompt.ts`: archived ones left out) answers with a prompt that tells the case and asks to go on or cancel, before `preHandle` takes any lock; the undo of a case is never asked about. It is thrown from `ModerationCommand#confirmRecentCase` as a `ModerationCommandPrompt`, after the role setup prompt. The command and its options wait in Redis (`wolfstar:moderation:confirm:<guildId>:<ownerId>:<promptId>`, the ID of the interaction of the command, 5 minutes), and the `moderationConfirm` interaction handler (`moderationConfirm.<ownerId>.<verb>:<promptId>`, moderator level, only the moderator who ran the command) runs it again with `execute(…, { confirmed: true })`
- **Thresholds of warnings:** `/warn-thresholds add|remove|list` (`src/commands/Management/warnThresholds*`, administrator level) sets what happens to a member who reaches a number of active warnings, up to 10 per guild (`MaximumWarnThresholds`), as rows of `GuildWarnThreshold` (`projects/database/src/settings/warnings/`, which the contract controls: the count, the period they are counted in, `0` for every one, the action among `WarnThresholdActions`, every hard action but a warning, and its duration). The `moderationEntryAddWarnThreshold` listener runs on every warning that is added, by a command, a report or the auto-moderation: `findReachedWarnThreshold` (`lib/moderation/warnThresholds.ts`) takes the threshold with the highest count whose number of active warnings (`countActiveWarnings`: not removed, archived nor a removal, within its period) is exactly its count, so a threshold is reached once and not by every warning past it, and `applyWarnThreshold` takes its action as the bot, a case like the ones of the commands. No direct message is sent. They are cached per guild and broadcast as `warnThresholdsUpdate`
- **Message of a case:** the moderation commands take a `message` option, the link of a message of the guild or its ID (`resolveMessageReference` in `ModerationCommand.ts`), where they used to take an image. It is the `messageReference` of the entry (`{ channelId, messageId }`). The table of the cases is owned outside this repository and has no column for it nor for `extraData`, so the manager stores both in `ModerationCaseData` (`projects/database/src/settings/cases/`) and reads them back with the case: the embed of the case links to it. `ModerationCommand` forwards the message to the moderation log before it takes the action (`forwardCaseMessage` in `common/util.ts`, a `message_reference` of type `Forward`), since a ban or a softban deletes the messages of the user and a forward keeps what the message said; the ID of the copy is the `forwardedId` of the reference, the case `moderationEntryAdd` sends replies to it, and the copy is deleted when the action fails. A forward that fails (the message is gone, the channel cannot be read) is only logged, and the case is sent without it
- **Appeals:** with `appeals.enabled` (the table `GuildAppeals`, which the contract controls: `appeals.channel`, `appeals.bans`, `appeals.mutes`, `appeals.timeouts`, `appeals.questions`, one per line, five at most), the direct message of a ban, a mute or a timeout links to `wolfstar.rocks/appeal/<guildId>` (`getAppealUrl` in `lib/moderation/appeals.ts`; the case has no number yet when the message is sent, so the page lists what can be appealed). The website reads `GET /appeals/:guild` (the cases of the logged-in user that can be appealed, `findAppealableCases`: the latest one in course of each enabled type, and the questions, the default one when the guild set none) and posts `POST /appeals/:guild/:case` (`{ answers }`, one per question); the user does not need to be a member, a banned one is not. Each case is appealed once, as a row of `Appeal` (`projects/database/src/settings/appeals/`), and is sent to `appeals.channel` with `Accept` and `Deny` buttons (`renderAppealMessage` in `lib/moderation/appealService.ts`). The `appeal` interaction handler (`appeal.<appealId>.<verb>:<submit>`, moderator level) asks for the reason in a modal, decides the appeal once (`decideAppeal` only changes a pending one, so two moderators cannot both decide it), undoes the case in the name of the moderator when it is accepted (the appeal is pending again when the undo fails), tells the member in a direct message and replaces the buttons with the decision. The form and the review page are wolfstar.rocks#468
- **Message histories:** `/archive create|list|show` (`src/commands/Moderation/archive*`, moderator level) saves the messages a member sent in the last 14 days, optionally for a case, and answers with them as a text file (`getMessageHistoryFile` in `lib/moderation/historyReply.ts`). `collectMemberMessages` (`lib/moderation/histories.ts`) reads the latest page of the 50 text channels with the latest messages the bot can read (`MaximumHistoryChannels`, a request each) and keeps up to 200 messages of the member (`selectHistoryMessages`, the attachments as their links). The `archive` option of `/ban add`, `/softban` and `/kick` (the `archive` flag of `applyModerationBuilder`) saves them before the action, which deletes them, and links the history to the case once it exists; a history that fails does not keep the action from being taken. - **Sticky nicknames:** `/setnickname` takes a `sticky` option that keeps the nickname of a member, in the row of `StickyNickname` (`projects/database/src/settings/nicknames/`, one per guild and user, which the contract controls: its migration is applied before the bot is deployed), and the `guildMemberAdd` listener sets it back when the member joins again (with `Manage Nicknames`, and the bot above them in the hierarchy, as the sticky roles are given back). It is only the moderators who remove it: resetting the nickname with the command drops it, even when the member has none at the time, and so does setting another nickname that is not sticky. `/sticky-nickname` (`src/commands/Management/Members/stickyNickname.ts`, moderator level) shows it. A member who changes the nickname by themselves while in the server is left alone: taking `Change Nickname` away from them covers that
- **Dehoisting:** with `moderation.dehoist` (`GuildModeration.dehoist`, off by default, the column added by hand as the one of the time zone), the names of the members are cleaned as the Fire bot does, when they join (`guildMemberAddDehoist`) and when the name they show changes (`guildMemberUpdateDehoist`: a nickname that did not change is skipped). `getDehoistChange` (`lib/moderation/dehoist.ts`, a pure function) works it out from the nickname, the display name and the username: a name that starts with what lists it above the others (spaces and the ASCII punctuation from `!` to `/`) loses it, and one with characters that are neither printable ASCII nor Latin-1 (fancy fonts, zalgo, symbols, emojis, other scripts; the accents stay) is turned into plain ASCII with `@aero/sanitizer`, the library Fire uses. When less than two characters are left, a nickname is removed if the name shown without it is clean, else the username is cleaned in its place, else the nickname is `dehoisted`. `dehoistMember` leaves alone a member with a sticky nickname, one who can manage nicknames and one whose highest role is not below the one of the bot (`comparePositionTo`, which breaks a tie of positions by the ID of the role as Discord does), so it never fights a moderator nor asks Discord for an edit it refuses. It reads the sticky nickname and the member again, and renames them, under the lock `/setnickname` takes around its own write (`withNicknameLock` in `lib/moderation/common/nicknames.ts`, `nickname:<guildId>:<userId>`), so a sticky nickname a moderator sets while the checks run is not overwritten
- **Role rules:** `/role-rules add|remove|list` (`src/commands/Management/roleRules*`, administrator level) keeps a role in sync with the other roles of a member: it is given when the member has every `requires` role, one of the `any-of` ones (when there are some) and none of the `without` ones, and taken when they stop meeting it. Up to 10 per guild (`MaximumRoleRules`), rows of `GuildRoleRule` (`projects/database/src/settings/roles/`, which the contract controls). The `guildMemberUpdateRoleRules` listener runs on every change of the roles of a member (`getRoleRuleChanges` in `lib/roles/rules.ts`, a pure function) and gives and takes them in one edit, but the roles the bot cannot manage. A rule never reads its own role nor the role of another rule, and no rule reads the role it gives (`checkRoleRule`), since two rules that give and take each other's role would never settle; so the edit comes back to the listener and finds nothing to do. A rule applies the next time the roles of a member change, the members are not scanned when it is added. They are cached per guild and broadcast as `roleRulesUpdate`
- **Tracing:** `@wolfstar/plugin-opentelemetry` (wolfstar-project/plugins), in two parts. Its preload, `@wolfstar/plugin-opentelemetry/preload`, loaded with `--import` by the `start` script, starts the OpenTelemetry SDK before the bot imports anything, and only on the main thread (a worker thread inherits `--import`: the regular expression workers of the moderation would each start an SDK) when an OTLP endpoint is set (`OTEL_EXPORTER_OTLP_ENDPOINT`, which Railway sets with the protocol, the headers and the name of the service when tracing is on for it; nothing in the repository names an endpoint). It registers the loader hook of `import-in-the-middle` first, since the bot is ES modules and the libraries it imports would stay unpatched, then starts the SDK with the automatic instrumentations of `@opentelemetry/auto-instrumentations-node`: the `http` server (W3C trace context, so a request continues the trace of the edge), `pg` (the driver of Prisma 8, which has no tracing of its own: `@prisma/instrumentation` is for the engines of Prisma 5 to 7), `ioredis`, `undici` (Discord's REST) and the `http` client (InfluxDB). The package also replaces the token in the URL of a request to a webhook or an interaction of Discord with `REDACTED` in the spans of `undici`, does not trace the requests of the transport of Sentry (the key of the DSN is in their query) nor the handshake of a WebSocket (the gateway's, whose context lasts for hours: every span of the gateway went into one trace that never closed), and hides the `OTEL_EXPORTER_OTLP_*` variables while it creates the exporter of Sentry, so Railway's token is not sent there; its own tests cover all of it, the bot has none for it. Its module, `@wolfstar/plugin-opentelemetry/module` in `modules` of `stars.config.ts`, opens a span for every command, component and modal (`command <name>`, with its outcome, guild and channel; autocomplete is off), the parent of the spans of what it runs; without an SDK the spans are no-ops. The commands of Redis made for a dispatch are not traced (`ioredis` only traces a command under a span, and a dispatch has none), and its queries are traces of their own. The Dockerfiles turn off the metrics and the logs (Railway's receiver takes traces only), the cloud resource detectors and the `net` and `dns` spans. Sentry sets up no tracer provider of its own (`enableOpenTelemetrySetup` is off by default in Sentry 11), and `initializeApp` gives it `openTelemetryIntegration` (`getSentryIntegrations`, `lib/utilities/sentry.ts`), which puts what it captures (errors, logs, metrics, check-ins) on the trace and the span that are active, so an error in Sentry has the trace ID Railway shows. The spans go to two places: Railway, through the exporter the environment configures (picked by `OTEL_EXPORTER_OTLP_PROTOCOL` as the SDK does: http/protobuf on Railway), and the Sentry project of `SENTRY_DSN` when it is set, as JSON. Without `SENTRY_DSN` only Railway gets them, and without an OTLP endpoint nothing starts, even with `SENTRY_DSN`. The SDK listens to `SIGTERM` once and leaves the end of the process to the other handlers (a listener keeps a process from ending on the signal, and the broker consumer of a worker only raises it again when nobody listens); a process with no other handler ends once the spans are exported. The shutdown exports the last spans before the process exits (`flushTraces` in `lib/utilities/shutdown.ts`, the one of the package with a timeout of 5 seconds, in `closeTelemetry` with `closeLogger`). Leave the automatic instrumentation (OBI) of Railway off for the service: with the SDK it records every span twice
- **Analytics:** `@wolfstar/shared-influx-pieces` is listed in `modules` of `stars.config.ts` (its `/module`, the CLI would not inject a `/register` for it anyway, since it is no `plugin-*`): when `INFLUX_ENABLED` is on and `INFLUX_URL`, `INFLUX_ORG`, `INFLUX_BUCKET` and `INFLUX_TOKEN` are set it creates `container.influx` (`InfluxClient`, the write and query clients) and loads its own listeners, which count the interactions, write the `commands` points and the approximate server count. The listeners of `src/listeners/analytics/` extend `AnalyticsListener` (`lib/structures/listeners/`, an `InfluxListener` of the same package that is disabled when `isInfluxInitialized()` is false: the base class spreads the options of the piece after its own check, and the loader gives `enabled: true`, so a plain `InfluxListener` would run with no client; `emitter: 'client'` goes in their options) and write what the shared ones do not: the server and user counts with their `shard` tag, the message count (`countMessage` and `takeMessageCount` in `lib/utilities/analytics.ts`) and the resource points; `poststats` and `syncResourceAnalytics` trigger the periodic ones. Do not write a `commands` point there: the shared `commandRun` listener does.
- **Lockdowns:** `/lockdown` keeps what each lockdown changed in the Redis hash `wolfstar:lockdowns` (`LockdownManager`), and a temporary one has a `moderationEndLockdown` job whose ID is the lockdown key, so both survive a restart. A lockdown is remembered, and its release scheduled, before Discord is asked to change anything, and forgotten again when Discord refuses.
- **Reports:** a member reports another one to the moderators with `/report`, or from the Apps menu with `Report Message` and `Report User` (`src/commands/Moderation/report.ts`, no default member permissions). The context menu commands ask for the reason in a modal, and what is reported waits in Redis meanwhile (`wolfstar:reports:pending:*`, `lib/moderation/reports/pending.ts`), since a modal only carries IDs back; the same file holds the claims that stop a member from reporting more than once a minute and a message from being reported twice in a day. Every report is a row of `Report` (`projects/database/src/settings/reports/`), created before its message is sent, since the components carry its ID (`report.<reportId>.<verb>:<messageId>:<submit>`, `lib/moderation/reports/ids.ts`). The message is Components V2 (`lib/moderation/reports/render.ts`), sent to `reports.channel` with a mention of `reports.role`, in the language of the guild: blocks of text a separator apart (the title with the report and its date, who is reported, who reported, the reason, and for a message what it said), then buttons for `Warn`, `Timeout` and `Kick`, a menu for `Mute`, `Softban`, `Ban` and `Block the reporter` (`Unblock the reporter` when they are blocked, the menu is replaced when a moderator toggles it), and buttons for `Delete message` and `Dismiss`. The `report` interaction handler (`src/interaction-handlers/report.ts`) requires the moderator level, closes the report in the database before it takes the action (so two moderators cannot act on one report, and it is opened again if the action fails), and takes the action through `checkTargetCanBeModerated` (`lib/moderation/common/checks.ts`) and the `ModerationAction` of the type, so it is a case like the ones of the commands. A closed report loses its components and gains a status line, and its reporter is told in a direct message when `reports.notify` is on. With `reports.anonymous` the message and the history do not show who reported, the database still does. `/reports history|block|unblock` (`src/commands/Moderation/reports*`) lists the latest reports and manages `reports.blocked-users`. The settings are the table `GuildReports`
- **Auto purge and auto delete:** `/autopurge enable|disable|list` purges a channel every interval (5 minutes to 14 days) of every message or of the ones a filter looks for, and `/autodelete enable|disable|list` deletes the messages sent in a channel at once or a delay after (24 hours at most), but the ones that match what it keeps (`src/commands/Management/autopurge*`, `autodelete*`, helpers in `lib/moderation/cleanup/commands.ts`). Both are rows of their own, `GuildAutoPurge` and `GuildAutoDelete` (`projects/database/src/settings/cleanup/`), one per channel, up to 10 and 25 per guild. The filters are one pure function, `matchesCleanupFilter` (`lib/moderation/cleanup/filters.ts`). The `autoPurge` task runs every minute, takes the purges whose `nextRunAt` is due, gives each its next time before it runs it (`lib/moderation/cleanup/purge.ts`: up to 1000 messages, never the pinned ones nor the ones older than 14 days, which Discord does not delete in bulk) and drops the ones whose channel is gone. The `messageCreateAutoDelete` listener checks every message against the automatic deletions of its guild, which `lib/moderation/cleanup/store.ts` caches and broadcasts as `cleanupUpdate`; a delayed deletion is an `autoDeleteMessage` job, so it survives a restart, and it keeps a message that was pinned meanwhile. `lib/moderation/cleanup/messages.ts` has the history reading and the bulk deletion `/prune` shares with the purges
- **Automatic messages:** `/automessage enable|disable|list` (`src/commands/Management/automessage*`, administrator level, helpers in `lib/automessages/`) sends a message in a channel again every interval (10 minutes to 14 days, `AutoMessageIntervalLimits`), one per channel and up to 10 per guild (`MaximumAutoMessages`), rows of `GuildAutoMessage` (`projects/database/src/settings/messages/`, which the contract controls). `enable` takes the channel, the interval and whether the mentions of the message ping (`mentions`, off by default: `allowed_mentions` parses nothing), and asks for the text in a modal, since an option of a command holds one line; the options wait in the custom ID of the modal (`automessage.<ownerId>.enable:<channelId>:<seconds>:<mentions>`, `ids.ts`), so nothing is kept meanwhile, and the `automessage` interaction handler writes it. The modal opens with the text the channel already sends, so `enable` again edits it. The `autoMessage` task runs every minute, as `autoPurge` does: it takes the messages that are due, gives each its next time before it sends it (`send.ts`), skips a channel whose last message is still the one the bot sent (`shouldSendAutoMessage`, the ID of the message it sent last is kept in the row), so an idle channel does not fill up with it, and drops the ones whose channel is gone. It reads each one again under the lock `/automessage` writes with (`withAutoMessageLock`, `automessages:<guildId>`), so one that was disabled or edited after the batch was read is not sent as it was, and it waits for the gateway (`waitForReady`). The automatic messages are read by the commands and the task only, so they are not cached
- **Honeypot:** a channel no member has a reason to write in, so who does is a spam bot or a hacked account. Its settings are the table `GuildHoneypot` (`honeypot.channel`, `honeypot.log-channel`, `honeypot.action`, `honeypot.direct-message`, `honeypot.warning`, `honeypot.random-name`, `honeypot.keep-active`), which the contract controls: its migration is applied before the bot is deployed, as the one of `GuildReports`. The `messageCreateHoneypot` listener gives the messages of the users (not of the bots, the webhooks nor the system) sent in `honeypot.channel` to `catchHoneypotMessage` (`lib/moderation/honeypot/catch.ts`): a moderator is left alone, the message is deleted, and the `ModerationAction` of `honeypot.action` (`Kick`, `Softban` or `Ban`, the last two delete what the member sent in the last hour in every channel) is taken as the bot, so it is a case like the ones of the commands, with the direct message when `honeypot.direct-message` is on and the user did not turn them off. A member is claimed in Redis for a minute (`wolfstar:honeypot:caught:<guildId>:<userId>`), so the messages a bot sends in a row make one case; without a ready connection the process keeps the claim itself. The catch, or the reason Discord gave for refusing the action, is sent to `honeypot.log-channel` (`renderHoneypotLog` in `log.ts`, what was sent is quoted in a code block so its links cannot be followed, and the quote is a block of its own: `createLogMessage` takes an array of blocks it keeps whole, where a text is split every 1024 characters and a code block would lose its fence). `/honeypot setup|edit|disable|show` (`src/commands/Management/honeypot*`, administrator level, helpers in `lib/moderation/honeypot/commands.ts` and `channel.ts`) writes those settings and answers with their summary: `setup` takes a channel or creates one at the top of the list (`createHoneypotChannel`), and refuses a channel the bot lacks a permission in (`getMissingHoneypotPermissions`, the ones of the channel plus the one of the action). Before it creates one it asks whether the bot has them in the guild (`getMissingHoneypotGuildPermissions`), and a channel it created that did not become the honeypot is deleted (`deleteHoneypotChannel`), so a setup that fails leaves no channel behind. `setup` and `edit` refuse a `logs` channel the bot cannot post in (`getMissingHoneypotLogPermissions`, what `canSendEmbeds` asks for in `guildMessageLog`). The warning of the channel is a message of the bot that is tracked by its ID, in the Redis hash `wolfstar:honeypot:notices` (`<guildId>` → `<channelId>:<messageId>`, as the lockdowns are; the process remembers it without a ready connection) and not in the settings, which would need a column and a migration for something no server configures: it is the only message the bot deletes there, the channel is never scanned. When the dashboard changes `honeypot.channel`, `honeypot.action` or `honeypot.warning`, the `dashboardSettingsUpdateHoneypot` listener puts the warning in order the same way (`followHoneypotSettings` in `dashboard.ts`, under `withHoneypotLock` on the settings read inside it: taken off with no channel, sent again otherwise), writes nothing back when it cannot, and tells `honeypot.log-channel` (`commands/honeypot:dashboardNoticeFailed`), or logs. The Redis hash of the warnings keeps the action each one tells about (`<channelId>:<messageId>:<action>`), so a reconcile sees a warning that tells another action; one kept before has none, and is taken to be right. `refreshHoneypotNotice` sends the new warning first and then deletes the tracked one, wherever it is, so a channel the honeypot moved from keeps none and a warning that cannot be sent leaves the old one in place (it returns `false`); `setup` calls it, `edit` when the warning or the action it tells about changes, and `disable` takes it off (`removeHoneypotNotice`). The three write the settings and change the warning under one lock (`withHoneypotLock`, the shared lock `honeypot:<guildId>`) and read the settings again inside it, so an `edit` and a `disable` at the same time do not leave a warning in a channel that is no longer a trap. The `honeypotUpkeep` task runs every hour and keeps up the channels whose hour of the day it is (`getHoneypotUpkeepHour`, from the ID of the guild, so the guilds are spread over the day): `fetchHoneypotUpkeeps` (`projects/database/src/settings/honeypot/`) reads the ones with `honeypot.random-name` or `honeypot.keep-active`, and `runHoneypotUpkeep` (`upkeep.ts`) gives the channel another of `HoneypotChannelNames` (names no member would post in, never `honeypot` nor one that invites them to write: who writes there is kicked or banned) and sends the warning again, deleted at once when the guild keeps none; a channel that is gone turns the honeypot off. The task read the honeypots a moment before, so the upkeep runs under `withHoneypotLock` and does what the settings say now, read from the database (`writeSettingsTransaction`): a channel that was disabled or replaced meanwhile is skipped, and the settings are only cleared of the channel that is gone, never of the one that took its place. It answers `failed` when the message of the day could not be sent, which the task logs, and the warning the channel had stays

- **Join Guard:** stops the members whose account looks like a raid or a spam bot when they join (wolfstar#298), with a checkpoint on wolfstar.rocks in the spirit of AltDentifier. Its settings are the table `GuildJoinGuard` (`join-guard.*`, a child of `Modules` as `GuildHoneypot` is), which the contract controls with the four tables of rows next to it: `GuildJoinGuardRule` (up to 10 rules, `MaximumJoinGuardRules`, names unique whatever their case by an index made by hand), `JoinGuardCheckpoint` (one row per member the guard stopped, the queue of the dashboard; a partial unique index made by hand keeps one `Waiting` row per member and guild), `JoinGuardRequest` (what the website asks) and `JoinGuardSharedBan` (the accounts banned for raiding or scamming, by the guard or by the `Ban` and `Softban` of the honeypot, which the checkpoint of every guild reads; it has no relation to the guild, so it outlives it). The storage is `projects/database/src/settings/joinguard/`, and the bot is `lib/moderation/joinguard/`. The dashboard writes the settings and the rules in the database itself and tells the bot nothing, so the guard reads them from their tables (`fetchTableSettings`, which reads one table of the settings with no other) and keeps them 10 seconds at most (`readJoinGuardConfig`, `JoinGuardConfigLifetime`), dropped at once by the bot's own writes (`announceJoinGuardChange`, the shard message `joinGuardUpdate`). The bot writes the rules only to forget a role or a channel that was deleted (`roleDelete`, `channelDelete`): one conditional update, which reads nothing back so it takes no lock, and tells the other processes only when a rule changed. The shared lock `joinguard:<guildId>` is taken by the post of the checkpoint button. The `guildMemberAddJoinGuard` listener runs `guardJoiningMember` (`join.ts`): nothing while the guard is off, nor for an allowed user or a member who holds an allowed role, the sticky roles they get back included; otherwise every enabled rule whose conditions all match (`conditions.ts`, pure: the age of the account from its ID, no avatar of its own, a name that looks generated by `isGeneratedName`, conservative since a false positive stops a person, a text of the name matched after the confusables normalization of the auto-moderation, an app without the verified bot flag) runs, combined once by `planJoinGuardActions` (`plan.ts`, pure): a ban beats a kick, which beats the checkpoint, the first rule of the strongest decides it and is the one the row names; the roles and the alerts are of every rule; one direct message, sent first when the member is removed, carrying the checkpoint link or the appeal link. Kicks and bans are cases of the bot (`ModerationActions`, the reason names the rules, no direct message of the case), refused before the direct message when the checks of the moderation commands would refuse them (`getJoinGuardTargetProblem`: the owner, a member at or above the bot), and a ban goes on the shared ban list (`recordSharedBan`). The checkpoint (only when `join-guard.checkpoint` is on, and never when the pending and the verified roles are one role, which the `manageableRole` serializer refuses, on the settings as they end up: the settings route validates every change of a write on the others applied, `validateSettingsChanges` in `lib/database/settings/validation.ts`, so a write that swaps the two roles is accepted) is set up whole or not at all: it gives the pending role, inserts a `Waiting` row with the signals and `expiresAt`, and schedules `joinGuardCheckpointTimeout` (payload `{ checkpointId }`, job ID `joinguard-checkpoint-<id>`, tried again for about five hours when the kick fails, the job throwing then) unless the timeout is 0; a pending role that cannot be given leaves the member not stopped (the timeout would read the missing role as let in by hand), and a row or a job that cannot be written takes the role back and deletes the row. The sticky roles a member gets back on join are given one request at a time (`guildMemberAdd`), since a list replaces the roles of the member with a snapshot that lacks the pending role. Every change of the state of a member (`checkpoint.ts`: the page, `/verify`, a kick of the dashboard, the timeout, `guildMemberRemoveJoinGuard` that marks the leave) runs under the shared lock of the member (`joinguard:<guildId>:<userId>`, not of the guild: the members of a raid would wait for each other past the time a lock is waited for) and resolves the row first, only while it waits (`resolveJoinGuardCheckpoint`), then acts, and makes it wait again when Discord refuses (`reopenJoinGuardCheckpoint`); letting a member in gives the verified role before it takes the pending one, and takes it back when that fails, so a member never has neither role: so an old job does nothing to a member who was verified, let in, kicked, who left or joined again (a new stay has a new row), and the timeout resolves as let in by hand a member who lost the pending role or got the verified one. The bot checks its own permissions before it acts (`permissions.ts`: the roles below its highest one, kick, ban, posting in the channels) and every result goes to `join-guard.log-channel` (`renderJoinGuardLog`), the errors included. The website inserts a `JoinGuardRequest` (`Pass`, `Verify`, `Kick`, `PostButton`) and runs `NOTIFY join_guard_request, '<id>'` in the same transaction: the connection that hears the website (see **Cache** in **Settings System**) hands them to the `JoinGuardRequestQueue` (`queue.ts`) of the gateway process, or of the first shard with the sharder (`joinGuardRequest`, which the shard manager sends it), started by the `websiteNotifications` listener on `clientReady`, which also sweeps every 30 seconds and at the start the requests nobody claimed for 5 seconds (a partial index made by hand). A `Kick` gets the checks of `/kick` against the user of the dashboard who asked (the website only decides who may ask). A request is leased in Redis for two minutes (`wolfstar:joinguard:request:<id>`, in the process without a connection), read again while its `processed_at` is null (`fetchUnprocessedJoinGuardRequest`), parsed (`parseJoinGuardRequest`), done one after the other, and only then marked done with one `UPDATE … WHERE processed_at IS NULL RETURNING` that also writes why it could not be done to its `error` as `<code>: <detail>` (`completeJoinGuardRequest`, through `updateAll`: `update()` reads the row first). A process that stops while it holds one leaves it to a sweep once the lease ran out, and doing it again is safe, every change of a member being made only while their row waits, and a request never acting on a member who joined again after it was made (`NotMember`) (`JoinGuardFailureCodes`, a contract with the website). `/joinguard show|post-button|enable|disable` (`src/commands/Management/joinguard*`, administrator level) shows the guard (its rules, the checkpoint, the stopped and waiting counts of the week), posts the checkpoint button (a link button to `wolfstar.rocks/verify/<guildId>`, which needs no handler; posting again edits the message of `join-guard.checkpoint-message`, the one setting only the bot writes, `notAllowed` for the API) and switches it; `/verify user:` (moderator level) lets a member in by hand. The rules are edited on the dashboard only. The settings menu has a `join-guard` group, with two key types of its own: `manageableRole` (a role the bot can give and take) and `joinGuardTimeout` (0, or from an hour to a week). The module emoji `module_join_guard` has to be uploaded to the applications

- **Edited message log:** `rawMessageUpdateNotify` shows the change of an edited message as the server chose with `logs.message-update-style` (`GuildLogsOptions.messageUpdateStyle`, `MessageUpdateStyle` of `wolfstar-database`): `Difference` (the default) is one text with the removed words struck through and the added ones in bold, `Separate` is the content before and the content after, each under its own title and escaped (`lib/utilities/functions/messageUpdate.ts`). `createLogMessage` takes the content as a list of parts too: each starts a block of its own, and when they do not fit the message together `fitLogParts` cuts the longest first. The footer links to the message in both styles. The settings menu edits the key with a select menu: a key whose type has a few fixed values is the `choice` kind of `lib/structures/settings-menu/values.ts` (`getSettingChoices` and `getSettingChoiceLabel` list them and name them)
- **Invite, thread, event, expression and integration logs:** five more `logs.*` channels (`logs.invites`, `logs.threads`, `logs.events`, `logs.expressions`, `logs.integrations`, columns of `GuildLogs` added by hand, as `timezone` was), each a `guildLogChannel` key, so it can be a thread and go through a webhook (`WebhookLogKeys`). The listeners are in `src/listeners/guilds/{invites,threads,events,expressions,integrations}/` and send through `sendSimpleLog` (`lib/moderation/logs/simple.ts`: the name of what the log is about, a few lines, what happened): invites created and deleted (with who made it, the channel, the uses and when it expires); threads created and deleted, and renamed, archived or locked (the other updates of a thread are not logged); scheduled events created, changed (name, status, time or place) and deleted (`lib/moderation/logs/events.ts`); stickers and soundboard sounds created, changed and deleted; apps added and removed, and the webhooks of a channel changing (Discord only says which channel). The client asks for the `GuildIntegrations`, `GuildScheduledEvents` and `GuildWebhooks` intents for them. `logs.boosts` (`GuildLogs.boosts`, the same kind of column) logs a member who starts or stops boosting the server (`src/listeners/guilds/boosts/`, `lib/moderation/logs/boosts.ts`): `getBoostChange` compares the time the member boosts since (`premium_since`) before and after an update of the member, so it needs the member to be cached, and a member who leaves while boosting is read from the member the cache held, since Discord sends no update for it. Discord does not say how many boosts a member gave, so a second boost of a member who already boosts is not seen, which the description of the setting tells
- **Logs in threads (experimental):** the channel of a log (`logs.*`, the keys of the `guildLogChannel` type that `logChannel()` in `configuration.ts` makes) can be a text or an announcement channel, as before, or a thread: the thread of a text channel, and the post of a forum, which is a public thread (the serializer is `serializers/channel.ts`, the select menu lists the thread types in `getSettingChannelTypes`). A forum or a media channel itself is not taken, since a message cannot be sent to it without making a post. The other channels of the bot (`moderationChannel`, `reportsChannel`, `honeypot.channel`, `honeypot.log-channel`, `automod.channel`, the ignored ones) stay text and announcement channels only. It is marked as experimental where the menu shows it: a flask on the key in the list and a note in its editor (`getSettingExperimentalNote`), since it is not tested in every case. Sending to a thread needs `SendMessagesInThreads`, not `SendMessages` (`LoggerManager` and `canSendEmbeds` ask for it by the type of the channel), and a locked thread needs `ManageThreads`; Discord unarchives an archived thread when a message is sent to it, so an archived one needs nothing. A thread that is deleted is an unknown channel, which clears the setting as a deleted channel does. With `logs.webhooks` on, the webhook of a thread is the one of its parent (a text, an announcement or a forum channel), and the log is posted in the thread with its `threadId` (`getLogWebhookTarget`): the record of `wolfstar:logs:webhooks` is by the parent, and the parent keeps its webhook while any log is sent to it or to one of its threads (`releaseUnusedLogWebhooks`, which looks the parent of each channel up). The name of a thread cannot be looked up by text, only by its ID or its mention, since the guild does not list its threads
- **Logs through webhooks:** with `logs.webhooks` on (`GuildLogsOptions.webhooks`, off by default), the logs are sent through a webhook of their channel, so the administrators give them a name and an avatar in Discord. Every log goes through `sendLogMessage` (`lib/moderation/logs/send.ts`), which `LoggerManager#send` and the `guildMessageLog` listener call where they used to call `channel.send`, so the listeners know nothing of it. It also drops the logs of the events of the server (a key that starts with `logs`, `isEventLogKey`) when `modules.logs` (`Modules.logs`, the `Events` module of the dashboard) is off; the moderation log, the reports and `honeypot.log-channel` go through it too and are sent whatever it is, since they are of other modules. A log goes through a webhook only when its key is one of `WebhookLogKeys` (`lib/moderation/logs/webhooks.ts`: the `logs.*` channels and `honeypot.log-channel`; a test lists them, so a new log has to be looked at). The moderation log (`moderationChannel`, the cases and what the auto-moderation sends there) and the reports (`reportsChannel`) stay messages of the bot: they are edited or replied to after they are sent, which the bot cannot do to the message of a webhook. So does a message a webhook cannot send (the forward of `logs.image`, `canSendThroughWebhook`) and a channel that is not a text channel, an announcement channel or a thread of one. There is one webhook per channel, whatever the number of logs sent there, made the first time a log goes there (`resolveLogWebhook`): the one that is remembered, else the one the bot already owns in the channel (`findOwnedLogWebhook`, Discord gives the token of a webhook to the application that owns it), else a new one with the name and the avatar of the bot, under the shared lock `log-webhook:<channelId>`, so a lost record or a second process does not pile them up (a channel holds 15). The ID and the token are kept in the Redis hash `wolfstar:logs:webhooks` (`<channelId>` → `<webhookId>:<token>`; the process remembers them without a ready connection) and not in the settings, which the dashboard, the export and the audit log read: the token is a secret, and what Redis loses is found again by listing the webhooks of the channel. It is never logged either: the URL of a request made through a webhook holds it, so `webhooks.ts` logs the code of an error and not the error. Finding or creating the webhook needs `Manage Webhooks` in the channel; without it, and whenever the webhook fails, the log is sent as a regular message, so none is lost (`sendThroughLogWebhook` answers `false`). An `Unknown Webhook` (it was deleted in Discord) drops the record, finds or creates the webhook again and sends once more; a channel whose webhook could not be made is not tried again for five minutes by that process. When a write of the settings leaves a channel with no log that uses its webhook (the channel of its last log changed, or `logs.webhooks` was turned off), `Transaction#submit` deletes the webhook with its token and forgets it (`getUnusedLogWebhookChannels`, `deleteLogWebhooks`, not waited for); a channel another log still points to keeps its own
- **Auto-moderation rules:** a guild has up to 25 named rules (`MaximumAutoModerationRules`), several of the same type if it wants, each with its own options, actions, threshold and exempt roles and channels. They are rows of `GuildAutoModerationRule` (`projects/database/src/settings/automod/`: `types.ts` has the types, the limits and `normalizeAutoModerationRuleOptions`, `storage.ts` the queries), not settings: the options of a rule depend on its `type` and are stored in the typed `options` JSON column (`AutoModerationRuleOptionsMap`). The bot reads and writes them through `src/lib/moderation/automod/rules.ts`, which caches them per guild, queues the writes of a guild and runs each on the rules the database has (pass a function to `updateAutoModerationRule` for a change that depends on the rule), broadcasts `automodRulesUpdate` to the other shards and keeps the state of each rule (infraction counter, word expression, mention buckets). A `ModerationMessageListener` (`src/listeners/moderation/messages/`) is given a `type` and applies the first enabled rule of that type a message infringes. `/automod` (`src/commands/Management/AutoModeration/automod*`, helpers in `lib/moderation/automod/commands.ts`) and the `guilds/:guild/automod/rules` routes (bodies read by `lib/moderation/automod/validation.ts`) manage them. `None` as the hard action takes none, for a rule that only deletes, alerts or logs, and is no step of an escalation. A rule can escalate its hard action: `escalation` (a typed JSON column, up to 10 steps of an action and a duration) takes its place for the members who keep reaching the threshold, the first step the second time and the last one from then on (`resolveAutoModerationRulePunishment`). `addAutoModerationRuleStrike` counts the hard actions a rule took on a member in Redis (`wolfstar:automod:strikes:<ruleId>:<userId>`, kept for the `escalationDuration` of the rule after the last one), so the count outlives a restart and is shared by the shards, and takes it back (`removeAutoModerationRuleStrike`) when the hard action was not taken; the menu edits both in the modal of its `Escalation` entry, a step per line (`timeout 1h`). A `Phishing` rule looks the hostnames of the links of a message up in the list of known phishing links of Discord-AntiScam (`lib/moderation/automod/phishing.ts`). The list is the copy in `projects/shared/src/links/PhishingHostnames.ts`, which `pnpm scripts:phishing` writes and the `update-phishing` workflow renews every day in a pull request (as `scripts:tlds` does for `TLDs.ts`; do not edit either). The bot never downloads it: a new hostname reaches it with the next image; a hostname of `allowed` is let through. The rules that only say whether a message infringes them (`Duplicates`, `Characters`, `Emojis`, `MassMentions`, `Spoilers`, `MaskedLinks`, `Polls` (a message with a native poll), and the ones that count within a period: `MessageSpam`, `ImageSpam`, `LinksCooldown`, `MentionsCooldown`, `StickersCooldown`, and `MessageDuplicates`, the same message among the last ones of a channel whoever sent it, which keeps them in the state of the rule) extend `AutoModerationRuleListener` (`lib/moderation/structures/`), which deletes, alerts and logs the same way for all of them with the keys `events/moderation:rule<Type>`, `…WithMaximum`, `…Alert` and `…Footer`; what they look for is a pure function of `lib/moderation/automod/detectors.ts`, and the ones with a `maximum` within a `timePeriod` count with `addAutoModerationRuleHits` (a `WindowCounter` in the state of the rule, per process). A `MessageSpam` rule counts the messages of each member in a channel, or with its `perChannel` option the ones of everybody in the channel together (`getMessageSpamCounterKey`), which the menu flips with a switch and `/automod edit` with `whole-channel`. A `MentionsCooldown` rule counts every mention as one, or with its `weighted` option a role mention as two and `@everyone` as five, which the menu flips with a switch and `/automod edit` with `weighted`. It took the place of the `NoMentionSpam` type, which banned by itself and left the response of the rule aside: `20261029T1302_merge_mention_spam_rules` rewrote those rules as weighted `MentionsCooldown` rules that ban at the first infraction and alert, made the enum again without the value, and an import of an older file upgrades them the same way (`upgradeRemovedRuleType` in `transfer/parse.ts`). The select menu that creates a rule tells each type with its `type<Type>Summary` (`AutoModerationRuleTypeSummaryKeys`), which has no numbers: the defaults read as fixed there. To add a type: the `GuildAutoModerationRuleType` enum of the contract (at its end, a native enum only takes new values there, and it needs a migration), `AutoModerationRuleTypes`, the options maps and the limits in `types.ts`, a listener, the `type<Type>` keys of `commands/auto-moderation.json` and a `menuOption<Type><Option>` key for each of its numbers, which the menu edits

## Environment (Varlock)

Configuration is described by [Varlock](https://varlock.dev) schemas instead of `.env.example` files. **Never read, print or edit `.env`, `.env.local` or `.env.*.local` files** (they hold real secrets; `.claude/settings.json` denies it). Read the schemas instead and validate with `pnpm exec varlock load --agent` (sensitive values are redacted). The `varlock` skill (`.agents/skills/varlock`) and the docs MCP (`.mcp.json`) are available.

- **Schemas:** one per package, sharing what is common through `@import`:
    - `.env.schema` (root): `NODE_ENV` (drives `@currentEnv`), `DATABASE_URL`, `TOLGEE_API_KEY`
    - `projects/database/.env.schema`: imports `DATABASE_URL` from the root
    - `projects/bot/src/.env.schema`: imports the shared items, declares everything the bot reads (`package.json#varlock.loadPath` is `./src/`). It generates `src/@types/env.d.ts` (do not edit it)
    - An import must also `pick` what the picked items depend on (`NODE_ENV`)
- **Values, lowest to highest precedence:** schema defaults → `.env.<NODE_ENV>` (tracked, throw-away local values only) → `.env.local` / `.env.<NODE_ENV>.local` (git-ignored) → the process environment. Deployed containers get theirs from the process environment.
- **Secrets:** never in a tracked file. Set them in a `.local` file or in the process environment. Only the items that are secret in production are `@sensitive` in production (`@sensitive=forEnv(production)`), so the committed local docker values are not flagged by `varlock scan`.
- **Loading:** `import 'varlock/auto-load'` is the first import of `src/main.ts`, `tests/setup.ts`, `projects/database/src/index.ts` and `prisma.config.ts`; it validates the environment and fills `process.env`. Wrap other commands with `varlock run -- <cmd>` (the `tolgee:*` scripts do). `varlock scan --staged` runs in the pre-commit hook.
- **Adding a variable:** declare it in the schema of the package that reads it (with `@type`, `@required`/`@optional`, `@sensitive` when it is a secret), add a local value to `.env.<NODE_ENV>` only if it is not a secret, then run `varlock load`.
- **Tests:** `NODE_ENV=test` selects `.env.test`; Discord and Redis are not required there.

## Database

- **ORM:** Prisma ORM 8 (`@prisma/orm-postgres`), accessed via `db` exported from `projects/database`
- **Contract:** `projects/database/src/contract.prisma`
- **Generated client:** `projects/database/src/generated/prisma/`
- **Prisma config:** `projects/database/prisma.config.ts`
- **Migrations:** Prisma 8 migrations in `projects/database/migrations/app/` (the contract snapshots are in `migrations/snapshots/`, `migrations/app/refs/db.json` is the `db` ref, the contract the next plan starts from). Most models are `@@control(external)`: the schema of those tables is owned outside this repository, so a migration only has what the contract controls, and a model that stops being external gets its DDL from `prisma migration plan` (and a model that is removed from the contract gets a `DROP TABLE`). To change a controlled model: edit `contract.prisma`, `prisma contract emit`, `prisma migration plan --name <slug>`, review the migration, and apply with `prisma db migrate --db "$DATABASE_URL"` (`--to <directory>` stops at one). A migration that copies data or creates what PSL cannot say (an index on an expression) is written by hand with `rawSql` in the `migration.ts` of the planned one, then `node migration.ts` attests it again. An index of an external model has no DDL either (`migration plan` fails with `MIGRATION.PLANNING_FAILED`): declare it in the contract with `map:`, scaffold the migration with `prisma migration new`, create it with `CREATE INDEX IF NOT EXISTS` in a `rawSql` (`20261018T1353_add_moderation_action_indexes`) and move the `db` ref; a data-only migration that does not change the contract is never run, since the route only follows edges that change it. A database that was not made by these migrations is signed once at the baseline contract with `prisma db sign`. `src/migrations/` is the old Prisma 6 history, which no longer matches the contract
- **Deploy:** every image brings the schema up to date before the bot starts (the `start` script runs `migrate:deploy` of `wolfstar-database`, `scripts/deploy.ts`, which does nothing out of `NODE_ENV=production`, and Railway's start command is `pnpm start`, so the `CMD` of the image would not do): a database with no `Guild` table gets `legacy/schema.sql`, a dump of staging at the contract of its `marker` row, since no migration creates the external tables, then `prisma db migrate` runs. A worker skips it, a failure keeps the bot from starting (a database with `Guild` and no marker stops it with what to do), and `DATABASE_MIGRATION_URL` is the connection it uses when `DATABASE_URL` goes through a pooler. Do not edit `schema.sql`: a change of the schema is a migration
- **Legacy tables:** whenever the database holds the tables of the old flat schema (`guilds`, `moderation`, `audit_event`…, under that name or the `<name>_v6` the website archives them with), the bot converts them at its start, on the gateway or the shard manager (`runLegacyMigration`, `lib/database/legacy.ts`, on `migrateLegacyDatabase` of `projects/database/src/legacy/`), and that is how a legacy backup is imported: restore it and restart. The mapping is pure (`guild.ts`, `automod.ts`, `cases.ts`, `logs.ts`), a test fails when a column of `guilds` is neither read nor in `NotCarriedColumns`, and it writes with `pg` (`insertMissing`, `ON CONFLICT DO NOTHING`), so what the new tables hold is never overwritten. Each guild is one transaction under an advisory lock, one that fails is logged and tried at the next start, and `LegacyMigratedGuild` remembers the ones that are done, so they are never read again. The legacy tables are left in place. What needs the loaded commands, Discord or the queue (the permission nodes, the jobs of the temporary cases) waits for `clientReady` (`legacyMigrationFollowUp`, `followedUpAt`)
- **Access:** `container.prisma` is the Prisma 8 `db` (type `Database` from `wolfstar-database`), set in `projects/bot/src/lib/setup/prisma.ts`. Query with `container.prisma.orm.public.<Model>` and `container.prisma.transaction(async (tx) => …)`
- **Middleware:** `db` runs the built-in `lints()` of Prisma (`@prisma/orm-postgres/family-runtime`): a `DELETE` or an `UPDATE` without a `WHERE` throws `LINT.DELETE_WITHOUT_WHERE` / `LINT.UPDATE_WITHOUT_WHERE` before it reaches the database. `budgets()` is not used: it refuses every `SELECT` without a `LIMIT`, which the settings storage and the moderation manager rely on
- **Types:** `Models.public_<Model>` from `wolfstar-database`; `BigInt` columns decode to `bigint`, `Jsonb` to `JsonValue`, `TimestampString(3)` to a branded string. That string has no time zone and holds UTC (`2026-10-08 13:02:18.076`): read it with `parseTimestamp` and write it with `formatTimestamp` (`projects/database/src/settings/time.ts`), never with `new Date(value)`, which reads it as the local time of the process
- **Typed JSON:** `prisma-orm-extension-typed-json` (replaces `prisma-json-types-generator`). A `Jsonb` column gets its TypeScript type from a `types { X = typed.Json("PrismaJson.X") }` entry in `contract.prisma`, and `PrismaJson.X` is declared in `projects/database/src/settings/types.ts`. The extension is registered in `prisma.config.ts` and in `db` (`typedRuntimeDescriptor`). The emitter drops `import(...)` expressions, so only global names work. It is only published for Prisma `8.0.0-rc.5`: `pnpm-workspace.yaml` overrides its Prisma packs to rc.13 and `patches/` adds the `dataType` that rc.13 requires from every codec. Drop both once it ships a rc.13+ build

## Settings System

- **Data:** `GuildData` (`projects/database/src/settings/types.ts`, exported by `wolfstar-database`) is flat. Its keys and their types are derived from the `Columns` map of `projects/database/src/settings/columns.ts` and from the models of the contract (`StoredGuildData`), so a column the table does not have, or a conversion that does not fit it, does not compile. Each key is prefixed by the Prisma 8 table it is stored in (`rolesAdmin` → `GuildRoles.admin`, `logsMemberAdd` → `GuildLogs.memberAdd`, `automodChannel` → `GuildAutoModeration.channel`, …). Snowflakes are strings in `GuildData`, `bigint` in the database
- **Time zone:** `timezone` (`Guild.timezone`, `UTC` by default) is the time zone of a guild, by its name in the IANA database (`Europe/Rome`); the `timezone` serializer takes it in any case and stores it as the database writes it (`resolveTimeZone` in `timezones.ts` of `wolfstar-shared`, the zones the runtime knows plus `UTC`). The dashboard edits it in the general settings, and the settings menu in a modal of five select menus (`renderTimeZoneModal` in `lib/structures/settings-menu/render.ts`, the `timezone` kind of `values.ts`): a select menu holds 25 values and the database some 400 zones, so `TimeZoneGroups` (`timezones.ts` of `wolfstar-shared`) has the 125 most used in five groups, nothing is selected, the zone the server has is told in the first label, and what is picked is the one the user chose (none keeps it, two is refused). A zone the runtime lists under another name (`Europe/Kiev` for `Europe/Kyiv`) is stored as the runtime has it (`getTimeZoneChoices`), which is what the serializer accepts. A zone of none of the groups is set on the dashboard, and the menu does not touch it. Nothing in the bot reads it yet: the times it shows are Discord timestamps, which follow the client. The table of the guilds is owned outside this repository, so the planner writes no migration for the column: `20261012T1146_add_guild_timezone` was scaffolded with `prisma migration new` and adds it by hand with `rawSql`, only when it is not there, since the migrations of the website may add it first; the `db` ref of a scaffolded migration is moved with `prisma migration ref set db <hash>`
- **Modules:** the `Modules` table has the switches the dashboard shows as modules, and each turns off what it names. `modules.automod` the auto-moderation rules (`ModerationMessageListener`). `modules.moderation` the commands of `ModerationModuleCommands` (`lib/structures/commands/modules.ts`: the actions, `/case`, `/archive`, `/prune`, `/lockdown`, `/slowmode`…, denied by the `commandsEnabled` precondition as `preconditions:disabledModuleModeration`); what configures it (`/reasons`, `/warn-thresholds`) and the reports are not of it. `modules.logs`, the `Events` module of the dashboard, the logs of the `logs.*` channels (`sendLogMessage`, see **Logs through webhooks**). `modules.roles` the initial roles, the role rules and the sticky roles given back on join, but the roles of a mute or a restriction, which are how a moderation action outlives a member leaving and are always given back (`getRestoredStickyRoles` in `lib/roles/sticky.ts`). `modules.autodelete`, `modules.autopurge` and `modules.automessage` the automatic deletions, purges and messages: the `messageCreateAutoDelete` listener and the `autoDeleteMessage` job (whose payload has the guild since; a job made before has none and deletes), and the `autoPurge` and `autoMessage` tasks, which give a purge or a message that is due while its module is off its next time and skip it, so turning the module on again does not run them all at once. What the channels are set up with stays, and the commands still configure them. The three columns were added by hand, as the one of the time zone (`20261025T2039_add_auto_modules`). `modules.honeypot` the honeypot: the `messageCreateHoneypot` listener catches nobody, and `runHoneypotUpkeep` answers `skipped`, so the channel is not renamed, written in, nor taken off the settings when it is gone. Its warning and its settings stay, and `/honeypot` still configures it. Its column was added by hand too (`20261030T2239_add_honeypot_module`). `modules.commands` turns off nothing and is not a setting
- **Updates channel:** `updates-channel` (`Guild.updates_channel_id`) follows an announcement channel of the support server, `UPDATES_ANNOUNCEMENT_CHANNEL_ID` (`getUpdatesAnnouncementChannelId` in `lib/utilities/updates.ts`): `#dev-announcement` (`1520758937807228998`, the default) for the alpha bot, `#announcement` (`890648971712802906`) for the public one. It works as the update channel of Dyno does: what is published there is posted in the server by Discord, through a webhook of the channel (`Manage Webhooks`). `Transaction#submit` calls `syncUpdatesChannelFollow` whenever a write changes the setting, whatever made it (the menu, the dashboard, a reset): the follower webhook of the previous channel is deleted, and the new channel follows, unless it already does. It is not waited for, and a follow that fails is only logged. Only the follows of the channel the variable names are deleted, so a server that was set before the variable changed keeps following the old channel until it removes the webhook
- **Storage:** `projects/database/src/settings/storage.ts` (`fetchGuildData`, `writeGuildData(db, …)`, in `wolfstar-database`) maps every key to its table and column, reads a guild from all the tables, and writes changes in one transaction. Missing rows are created in foreign-key order (`Guild` → `Modules` → `GuildAutoModeration`). A table of settings that the contract controls (`GuildReports`, `GuildLogsOptions`) needs its migration applied before the bot is deployed, since every read of the settings queries every table of `Tables`. What a guild configures that is rows of its own and not columns of the settings tables lives in a directory next to them, with the same split of `types.ts` and `storage.ts`: `settings/automod/` (the rules), `settings/reports/` (the reports) and `settings/cleanup/` (the automatic purges and deletions); `settings/ids.ts` has the check of a generated ID they share. To add a setting, add its column to the `Columns` map in `columns.ts`, its default to `constants.ts` (both in `projects/database/src/settings/`) and its key to `configuration.ts` (bot)
- **Cache:** In-memory `Collection<string, GuildData>` in `src/lib/database/settings/functions.ts`. A write of the bot drops the copies of the other shards (`settingsUpdate`). The dashboard writes the same tables and runs `pg_notify('guild_settings_update', '{"guildId":"…","keys":[…]}')` in the transaction of each write, the flat keys it changed and never their values: the one connection of the bot that hears the website (`createWebsiteListener` in `lib/database/website.ts`, on the `DatabaseNotificationListener` of `lib/database/notifications.ts`, which connects again with a growing delay, with TCP keepalive so a connection dropped without a word is found dead: `createWebsiteClient`) is in the shard manager with the sharder, or in the gateway process without it, and tells every shard `settingsUpdate` with the `keys` (`parseDashboardSettingsUpdate` refuses a payload that is not a write, with a warning). Only a write of the dashboard has `keys`: every shard then drops its copy and the caches of the rows the dashboard writes next to the settings (the auto-moderation rules, the automatic deletions, the reasons, the thresholds, the role rules, the join guard: their own messages, dispatched in the process, `lib/database/settings/dashboard.ts`), and the shard that has the guild (`isOwnGuild`, `shardIdForGuild`) emits `Events.DashboardSettingsUpdate(guildId, keys)` for what acts on a change. Every time the connection listens, the first time included, every shard drops everything (`settingsInvalidateAll`), since what was written while it did not is lost, and puts in order the warnings of the honeypots of its guilds that are out of step (`reconcileHoneypotNotices`; the rows of a guild the bot left are skipped). An invalidation also drops a read of the settings that is still running, so a read after a write never joins one that started before it. A worker of the broker hears none of it
- **Audit and command logs:** `AuditLogManager` writes every change of the settings and every command that is run as a row of `AuditEvent` (a hash chain). They are read on the web only (`guilds/:guild/audit-logs` and `guilds/:guild/command-logs`): there is no `logs.command` nor `logs.settings` channel to set, and nothing is sent to a channel of the guild
- **Context:** `SettingsContext` in `src/lib/database/settings/context/SettingsContext.ts`
    - Holds `PermissionNodeManager` and `AuditLogManager`
    - Has `update(settings, data)` for patching context on settings change
- **Structures:** `src/lib/database/settings/structures/` (PermissionNodeManager, AuditLogManager, Serializer, SerializerStore)
- **Schema:** `configuration.ts` describes every key (`SchemaKey`: type, range, default, `dashboardOnly`) in groups (`SchemaGroup`) by its dotted name
- **Serializers:** the pieces of the `serializers` store (`src/serializers/`, registered by `lib/setup/serializers.ts`), named after the `type` of the keys they handle (aliases included, e.g. `number` also answers `integer` and `float`). A serializer parses the text a user wrote (`parse(input, context)`), validates a stored value (`isValid`) and formats it (`stringify`, which may be asynchronous since roles and channels come from the gateway cache). `SchemaKey#parse/stringify/display` and `set`/`remove`/`reset` in `Utils.ts` go through them
- **`/settings`:** `src/commands/Management/settings.ts` is the parent of `/settings server` (`settings/server.ts`, administrator level, no default member permissions on the parent since everybody can open their own) and `/settings user` (`settings/user.ts`, the `User` model: `report`, the moderation direct messages; `lib/structures/settings-menu/user.ts`). The permission nodes and the dashboard `canManage` check the parent command, `settings`. `/settings server` opens the settings menu, a Components V2 message rendered by `lib/structures/settings-menu` (module select menu, one row per key with its edit button, paginated). The `conf` interaction handler (`src/interaction-handlers/conf.ts`) reads what a click does from its custom ID (`conf.<ownerId>.<verb>:<target>:<page>:<expiresAt>`), so the menu keeps no state. The menus of `/settings server` and `/settings user` close fifteen minutes after they were last used (`SettingsMenuLifetime` in `ids.ts`), with no collector and nothing kept: the time a component expires is the last part of its custom ID (`…:<page>:<expiresAt>`, in base 36), every click renders the menu again with a new one, the last line of the last container of the menu counts it down, and a click on an expired menu leaves it as it is and is answered with an ephemeral message that says so and mentions the command that opens it again (`renderSettingsExpired`); the first five clicks of a user on a message are (`claimSettingsExpiredNotice` in `expired.ts`, counted in Redis as `wolfstar:settings-menu:expired:<messageId>:<userId>`), the ones after them are only acknowledged. What is written in a modal is parsed, and what is picked in a select menu is validated, by the serializer of the key. It uses `@wolfstar/http-framework-utilities` for the custom IDs and for the reset confirmation (`MessagePrompter`), whose handlers `lib/setup/all.ts` registers with `@wolfstar/http-framework-utilities/register`
- **Auto-moderation menu:** every `/automod` subcommand but `delete` answers with it: `list` with the rules, the others with the rule they showed, made or changed (`replyWithAutoModerationRule` in `commands.ts`, what the command did is the notice above the section; an error is still a line of text). The menu also creates rules, a select menu of the types then a modal for the name, and so does the `Auto-moderation rules` entry of the `automod` page of the settings menu: a Components V2 message rendered by `lib/structures/automod-menu` (`render.ts`), the rules of the server with a select menu that opens one and the settings of the auto-moderation (`modules.automod`, `automod.channel`, `automod.track-native`, written with `writeSettings` by the `setting` verb), then the rule in three sections a select menu switches between: `options` (its list with `Add`, `Remove` and `Clear`, or its numbers in a modal), `response` (the soft actions as switches, the punishment select menu, then its duration and its threshold, the infractions within a period, each with the modal that edits it) and `exempt` (role and channel select menus, left out past the 25 values one holds). The `automod` interaction handler (`src/interaction-handlers/automod.ts`) reads what a click does from its custom ID (`automod.<ownerId>.<verb>:<ruleId>:<section>:<argument>`, `ids.ts`), requires the administrator level, and makes every change through `updateAutoModerationRule` with a function, on the rule the database has; what a change is, is a pure function of `actions.ts`.
- **Export and import:** the page of the general module of the settings menu has an `Export` and an `Import` button (the `export`, `import` and `importSubmit` verbs of `conf`). `Export` answers with a JSON file, and `Import` opens a modal (`renderSettingsImportModal`) that takes the file in a file upload, or what it holds pasted in a text input (4000 characters, a file that is attached wins), then shows what it would change and asks to confirm before it writes anything; both are administrator level and ephemeral. Nothing waits for the answer: what the file holds is kept in Redis for five minutes (`transfer/pending.ts`, `wolfstar:settings:import:<guildId>:<ownerId>:<importId>`, the ID of the submission of the modal, so two previews confirm their own file) and the buttons are answered by the `settingsImport` interaction handler (`settingsImport.<ownerId>.<verb>:<importId>`, administrator level), on whichever process gets the click, since with the sharder it is not always the one that showed the preview. The import is taken with `getdel`, so it is written once, and a click on one that expired takes the buttons away. The code is `src/lib/database/settings/transfer/`: `messages.ts` has the export and the preview the menu answers with, `attachment.ts` downloads the file, `format.ts` has the version of the file (`ConfigurationFileVersion`) and what it carries, `parse.ts` validates it, `plan.ts` works out the changes, `apply.ts` writes them, `render.ts` has the preview and `pending.ts` what waits for the confirmation. The file is `{ version, exportedAt, settings, automod: { rules } }`, the settings by their dotted name. What depends on the server stays out: a setting is carried when the `type` of its key is one of `PortableTypes` in `format.ts` (a boolean, a number, a text, a language, a command name, a choice between a few fixed values such as `honeypotAction` and `messageUpdateStyle`; not a role, a channel, a user or a permission node), and a rule has no `ignoredRoles` or `ignoredChannels`, which an import leaves as the rule has them. The file is not trusted: each value goes through the `isValid` of the serializer of its setting (what the dashboard does) and each rule through `parseAutoModerationRulePatch` (what the API does), after `checkAutoModerationRuleOptions` (`lib/moderation/automod/validation.ts`) checked its options as they are written, since the patch repairs what it reads (a wrong type takes its default, a number is clamped, a bad entry of a list is dropped) and a broken file would empty the options of a rule. A list of the options holds the 200 entries of `MaximumAutoModerationRuleListLength`, or as many as the rule of the server with the same name and type has, so the backup of a rule that was migrated with more is restored on it and a file cannot make a list grow past the limit (`findOversizedRuleLists` in `plan.ts` checks it again under the locks, and the import throws `ConfigurationImportStaleError` when the rule was shortened meanwhile). A rule of the file that is a Timeout with no duration is refused (`parseAutoModerationRulePatch`), but when the rule of the server with the same name and type is one too, which the menu saves before it asks for the duration, so its backup imports back; `findStaleTimeoutRules` checks it again when the import is written; and a file with one problem is refused whole with all its problems, a setting that is not one of the file included. A setting the bot no longer has is left out instead (`RemovedSettings` in `format.ts`: `modules.commands`, which turned off nothing, since the commands are not a module; the column stays in `Modules`, which is owned outside this repository), so a file exported before still imports. The settings the file does not have are left as they are; when it has an `automod` section the rules of the server become the ones of the file: the rule with the same name (whatever the case) and type is edited in place and keeps its ID, a rule of another type is deleted and made again, and the others are created or deleted, up to the 25 of `MaximumAutoModerationRules`. The rules of a type end up in the order of the file, since a message is held to the first enabled rule of a type it infringes and the order decides the punishment. The rules have no position: they are read by their ID, oldest first (`fetchAutoModerationRules`), and a new rule gets the last one. So the rules of a type that stay are the first ones of the file as long as the server has them in that order, and from the first rule that is new or out of place on, the rules of that type are made again in the order of the file (`PlannedRuleCreate#replaces`: the rule is deleted and created with its exempt roles and channels; it loses its ID, its strikes and its counters, which the preview says). An order that only differs is therefore a change, and importing the same file twice does nothing the second time. The order between rules of different types has no effect and is not kept. A `position` column would move a rule without making it again, at the cost of a migration and of every read and write of the rules knowing it. The write is one database transaction (`Transaction#submit(alongside)` takes what else to write in it, `writeAutoModerationRulePlan` writes the rules) and it is worked out again under the settings lock and the rules lock when the administrator confirms, from what the database has by then, not from the preview. It is audited as `guild.settings.update`, with the rules under `automodRules`. A new setting of a portable type is carried by the next export without a change here: `tests/lib/database/settings/transfer` lists the portable names, so adding one has to be looked at
- **`/commands`:** `src/commands/Tools/commands.ts` opens the commands menu, which takes the place of a `help` command: an ephemeral Components V2 message rendered by `lib/structures/commands-menu`, a command browser. A header container has the search button and the category select menu; the list is every command that can be run (`listCatalogEntries`: a command with no subcommands, or each subcommand of one that has them), numbered, five to a page, each with a pencil button that opens the modal of its command at once (administrator level). The modal holds the five components Discord allows: a Status radio, Enabled or Disabled, written to `commands.disabled` as the name of the command, which `lib/structures/commands-menu/disabled.ts` matches with the matchers of `lib/database/utils/matchers/Command.ts`, the select menus of the channels the command is allowed in, or ignores, and two mentionable select menus, one for the roles and users it is allowed to and one for the ones it ignores (the submitted data says which ID is a role and which a user, `setCommandMembers`; `CommandRestriction` in `restrictions.ts`). A rule names a command, or a group the matchers of `Command.ts` read: `Category.SubCategory.*`, `Category.*` or `*`, which the button of the title of a list and the select menu of its sub-categories open (`editGroup`, `renderGroupRuleModal`, the `.` of a target is a `~` in a custom ID), and the modal of a command tells the groups that apply to it too. `getCommandRulesDenial` decides (the `commandsEnabled` precondition orders only the roles a rule names, from the cache, so a command costs no request to Discord): a channel ignored by any rule that matches denies, and the allowed channels of the most specific rule that has some apply; then the most specific rule that names the member decides, else the highest of their roles a rule names (`@everyone`, the ID of the guild, is the lowest), with its most specific rule. An allowed entry is an exception to an ignored one that ranks below it, it limits nobody else: "only these" is `@everyone` ignored and them allowed, which the `Only the allowed roles and users` status of the modal writes (`withoutEveryone`), never the select menu, whose handling of `@everyone` is up to Discord. A list saved before this has no `{ format: 2 }` entry (`CommandRestrictionsFormat`, an entry of the column that is not a rule, which `writeCommandRestrictions` adds): `readCommandRestrictions` reads its rules that allow someone as ignoring `@everyone` too, so they keep meaning "only these" on every bot. What a select menu did not show, past its 25 entries, is kept (`keepHiddenRestrictionEntries`, `setCommandMembers`). The rules never give a member what the command asks for otherwise: its default member permissions and its `moderator` or `administrator` level still apply. They are `commands.restrictions`, the JSON column `GuildCommands.disabledInChannels`, which is read with `readCommandRestrictions` and never trusted: the table is owned outside this repository, and the column used to hold the commands each channel disabled, which are read as ignored channels. A thread is restricted as its parent, the administrators are not restricted, and a role or a channel that is deleted is taken out (`roleDelete`, `channelDelete`), a footer with the page and the count, and the first, previous, next and last page with a modal that goes to a page. `commands.disabled` and `commands.restrictions` are enforced by the global precondition `src/preconditions/commandsEnabled.ts`, whose denial the `chatInputCommandDenied` and `contextMenuCommandDenied` listeners reply to; `settings` and `commands` are never denied, so a server can always turn the commands back on. They replace the permission nodes, whose `permission-nodes` command is gone. `permissions.users` and `permissions.roles` stay stored until they are converted: with `COMMAND_RULES_CONVERT_NODES` on, which only the alpha bot sets, the `convertCommandRules` listener converts them once the gateway is ready (`fetchGuildIdsWithPermissionNodes`, `convertGuildCommandRules`, one transaction a guild, audited, and running it again changes nothing). `convertLegacyNodes` (`conversion.ts`, pure) turns what a node allows into allowed entries and what it denies into ignored ones, and converts a node whole or leaves it whole (`LegacyNodeSkip`: a name the bot does not have, `settings` and `commands`, which cannot be restricted, and a node whose allowed name covers a denied one as specific or more, since a node ran its allowed names first and the most specific rule would read it the other way, and a name that reaches `settings`, such as `*` or `Management.*`, since the nodes still decide who manages the server and no rule does); the nodes of a member who left are converted, the ones of a deleted role are dropped. An `allow` that only gave a command to a member without its level has no effect any more: a rule never grants. Until they are converted the nodes are still read for the access to the dashboard, never for the slash commands. The same two columns hold the dashboard access rules of wolfstar.rocks, entries with a `dashboard` key (`allow` or `deny`) and empty `allow` and `deny` lists (`AccessEntry` in `projects/database/src/settings/access.ts`): who may manage the settings of a server is `canManageServerSettings` (`lib/structures/commands/permissions.ts`), the rule the website applies in the same order: the owner, then the rule that names the member (their own in `permissions.users`, else the one of their highest role, `resolveAccess` of `wolfstar-database`, which decides on its own: `allow` without `Manage Server`, `deny` even for an administrator), then an administrator unless a legacy node denies them `settings`. The API (`canManage` in `lib/api/utils.ts`), `/settings server`, the `conf`, `settingsImport` and `commands` handlers and the settings of the auto-moderation menu ask it (the last ones after the `administrator` precondition, so a rule keeps an administrator out of them, it lets nobody in). `PermissionNodeManager` neither runs nor changes the rules, the removal of the legacy nodes keeps them, and they are not legacy nodes for the notice. While a server has some, the menu shows the administrators a notice with a button that sends them as a JSON file, each with why it was left (`legacy.ts`, `describeLegacyNodes`), and only the owner of the server removes them, by typing `REMOVE` in a modal that carries the revision of the nodes they downloaded. A search in a modal lists the entries it finds the same way. The commands come from `container.applicationCommandRegistry` (`catalog.ts`), so the menu shows what is registered to Discord, in the locale of the user; the category of a command is the first directory of its file. The `commands` interaction handler reads what a click does from its custom ID (`commands.<ownerId>.<verb>:<target>:<page>`), as the settings menu does
- **`/roles browse`:** `src/commands/Management/roles/browse.ts` opens the roles menu, an ephemeral Components V2 message rendered by `lib/structures/roles-menu`: a page that lists the roles of the server (`@everyone` included, highest first, eight to a page, the first, previous, next and last page and a modal that goes to a page), and a page that has only the select menu of the roles. Picking a role there shows it (what it is and what it can do) with the buttons that go back to the list or pick another one. The `roles` interaction handler (`src/interaction-handlers/roles.ts`) reads what a click does from its custom ID (`roles.<ownerId>.<verb>:<page>`); it is open to every member, as the roles of a server are

## Localization

- **Tooling:** [Tolgee](https://tolgee.io/) (migrated from Crowdin)
- **Config:** `.tolgeerc.cjs` (project id, locale↔Tolgee-tag mapping, push file list, pull output path)
- **Locale files:** `src/languages/{discordLocale}/{namespace}.json` (e.g. `en-US/globals.json`, `en-US/commands/admin.json`)
- **Typed keys:** `pnpm --filter wolfstar-bot i18n:generate` (`stars codegen`) regenerates `projects/bot/src/@types/i18next.d.ts` from `src/locales/en-US` via `@wolfstar/i18next-type-generator`; `stars codegen --check` fails when it is stale. Run it after editing `en-US` files, never hand-edit the output
- **Base locale:** `en-US` is push-only — it is the local source of truth and a pull never writes it
- **Pull remap script:** `scripts/tolgee-pull-remap.ts` — merges `tolgee pull` output from `.tolgee-pull/{tolgeeTag}/` onto the matching `src/languages/{discordLocale}/` files. It drops untranslated values (`null`, blank, empty ICU plural shells), rejects translations whose i18next placeholders don't match `en-US`, prunes keys `en-US` no longer defines, and rewrites files in repo style (tabs, trailing newline) keeping the existing key order — so the diff only ever shows real translation changes
- **Slash command names:** keys `name` / `*Name` whose en-US value is a valid Discord command name are lowercased on pull (Tolgee holds `Avviso` where Discord needs `avviso`); a name that cannot be made valid is rejected and reported. `tests/languages/locales.test.ts` fails on any uppercase localized name
- **Sanitizing helpers:** `scripts/lib/locale-sanitize.ts`, shared with `tests/languages/locales.test.ts` so the definition of a valid locale file lives in one place
- **Automated sync:** `.github/workflows/tolgee-sync.yml` runs `pnpm tolgee:pull` nightly (02:00 UTC), validates the result with `pnpm vitest run tests/languages`, and opens/updates a PR from the fixed `i18n` branch — don't hand-edit non-`en-US` locale files, they get overwritten by the next sync
- Requires `TOLGEE_API_KEY` in the environment for push/pull; never commit it

### REST API

When the bot is logged in, the embedded API listens on `API_HOST`:`API_PORT` (default `127.0.0.1:8282`). `GET /` returns `{"message":"Hello World"}` (`src/routes/index.get.ts`).

The routes are file-based (`src/routes/**`, `<path>.<method>.ts`). The OAuth2 routes (`src/routes/oauth/`) use `getAuth()` from `src/lib/api/utils.ts`, built from the `OAUTH_*` variables; they are disabled when `OAUTH_SECRET` is unset.

`GET /commands` (`src/routes/commands.get.ts`) lists the commands for the website, an entry for each command with no subcommands and for each subcommand of the others (`ban add`, `ban remove`, as the commands menu lists them, sorted by name), with the fields the message commands of the original bot had (`FlattenedCommand` of `src/lib/api/commands.ts`) and `command`, the name of the piece the settings take: `commands.disabled`, the restrictions and the permission nodes disable a command, not a subcommand, by its piece (`warnThresholds`, where Discord writes `warn-thresholds`), so the dashboard writes `command` and not `name`. The usage of an entry and the explanation of its options are read from what the command registers with Discord, in the language of `lang`; the rest of its help (`extendedHelp`, `examples`, `reminder`, `possibleFormats`) is the entry of its command in `src/locales/en-US/commands/help.json`, which every subcommand shares but for the examples (a subcommand gets the ones that start with its name, without it), keyed by the command as Discord writes it (`/ban`): with a bare name, a help keyed like a key of another namespace (`commands/moderation:permissions`) made the typings of i18next return an object for `t(key as TranslationKey)` (`CommandHelpTexts`). `tests/locales/commands.test.ts` asks every command for an entry and runs each example against `src/@types/commands.d.ts` (a subcommand it has, options it has, every required one), so a new command, subcommand or option needs its help looked at. The sub-category is the second directory of the file of the command (`Moderation/Restriction`, `Management/AutoModeration`, as the original bot named them), `guarded` is `ProtectedCommands`, the permission level is the one of a `moderator` or `administrator` precondition (else the one the default member permissions stand for), and the preconditions are the ones of its `preconditions` option, after `GuildOnly` for a command that only runs in servers. A subcommand adds the level `RequiresCommandPermissionLevel` requires to run its own piece (`subCommandsRegistry` of `@wolfstar/plugin-subcommands-advanced`), but not the `preconditions` option of that piece, which the plugin never checks: it runs `chatInputRun` of the piece for the command, which the decorator remembers for `getRequiredCommandPermissionLevel` (`/settings server` is administrator, `/settings user` everyone).
